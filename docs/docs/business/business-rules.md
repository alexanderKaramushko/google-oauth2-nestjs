# Бизнес-правила

## Назначение документа

Документ описывает действующие и запланированные правила аутентификации и
работы с локальным профилем пользователя. HTTP, cookie, коды ошибок и внутренние
компоненты описаны в [системной спецификации](../system/system-specification.md).

Для правил используются статусы:

- **Реализовано** — правило действует в системе;
- **Частично реализовано** — возможность существует, но не все ожидаемые
  гарантии обеспечены;
- **Запланировано** — возможность явно зафиксирована, но пока недоступна;
- **Требует проверки** — текущее поведение известно, но продуктовое решение не
  определено.

## Общие понятия

- **Пользователь** — человек, который подтверждает личность через Google.
- **Клиентское приложение** — приложение, запрашивающее аутентификацию.
- **Идентификатор приложения** — значение, по которому после входа выбирается
  клиентское приложение.
- **Локальный профиль** — сохранённые сервисом имя, идентификатор пользователя
  у провайдера и название провайдера.
- **Защищённая операция** — действие, доступное только после подтверждения
  пользовательской сессии.

## Аутентификация

### Начало входа

**Статус:** Реализовано

**Предусловия:**

- клиентское приложение передало свой идентификатор;
- Google OAuth настроен для auth-сервиса.

**Ограничения:** без идентификатора приложения начать вход нельзя.

**Результат:** пользователь переходит к подтверждению личности через Google.

### Подтверждение личности

**Статус:** Реализовано

**Предусловия:**

- пользователь завершил Google OAuth flow;
- запрос является продолжением ранее начатого входа;
- Google вернул профиль и авторизационные данные.

**Ограничения:** неподтверждённое или подменённое продолжение входа отклоняется.

**Результат:** пользователь считается аутентифицированным, а его локальный
профиль создаётся или используется повторно.

### Возврат в клиентское приложение

**Статус:** Требует проверки

**Правила:**

- если идентификатор зарегистрирован, пользователь возвращается в связанное с
  ним приложение;
- если идентификатор неизвестен, вход всё равно завершается, а данные
  пользователя возвращаются напрямую;
- неизвестное приложение не отклоняется до обращения к Google.

Продуктовое ожидание для неизвестного идентификатора приложения не определено.

## Пользователи

### Локальный профиль

**Статус:** Частично реализовано

**Правила:**

- пользователь определяется сочетанием идентификатора у провайдера и названия
  провайдера;
- при первом успешном входе сохраняются имя, идентификатор и провайдер;
- при повторном входе используется первая найденная запись;
- уникальность одного профиля для одной Google identity не гарантирована
  хранилищем;
- изменение и удаление профиля не поддерживаются.

### Получение собственного профиля

**Статус:** Реализовано

**Предусловия:** пользовательская сессия подтверждена.

**Результат:** возвращаются локальные профили с идентификатором текущего
пользователя у Google. При отсутствии записи возвращается пустой список.

## Доступ и сессия

### Защищённые операции

**Статус:** Реализовано

**Правила:**

- доступ разрешается только после подтверждения токена Google;
- одинаковая проверка применяется для защищённого HTTP-профиля и запроса
  пользователя внутренним сервисом;
- из токена используется идентификатор пользователя, по которому ищется
  локальный профиль.

### Выход

**Статус:** Реализовано

**Ограничения:** сессия Google не завершается, поэтому повторный вход может не
потребовать повторного ввода учётных данных Google.

**Результат:** локальная сессия в auth-сервисе завершается.

## Собственные токены

### Выпуск JWT auth-сервиса

**Статус:** Запланировано

**Правила:** планируется выпускать собственный JWT с асимметричной подписью
после подтверждения Google identity. Детали предложения находятся в
[ADR](../architecture/adr/own-jwt.md).

## Открытые вопросы

1. Должен ли неизвестный идентификатор клиентского приложения отклоняться до
   начала Google OAuth flow?
2. Должен ли локальный профиль быть строго уникален по паре «провайдер +
   идентификатор пользователя»?
3. Какие данные профиля разрешено возвращать клиентскому приложению напрямую?
4. Должен ли выход завершать только локальную сессию или также сессию Google?
5. Какие срок жизни, claims, правила ротации и отзыва нужны собственному JWT?
